# 真实报告测试后的工程优化安排

日期：2026-10-03。状态：**P0–P5 工程改造及 P6 离线验收已实施；用户真实模型复测待执行**。实际代码、验收证据和剩余边界见 [修复实施报告](POST_TEST_REPAIR_IMPLEMENTATION_REPORT.md)。

本文接续 `SYSTEM_RESHAPING_PLAN.md` 与 `UPGRADE_IMPLEMENTATION_REPORT.md`，依据用户发起的中国石油 E1-6 全选测试。下文保留改造的依赖顺序和验收要求；完成情况以实施报告逐项记录为准，真实业务验收不由离线测试代替。具体报告内容、模型响应、逐项结果和系统日志留在仓库外私有审计目录 `.local/audits/2026-10-03-petrochina/`；真实 OCR/IR/抽取产物保持原样。

## 1. 这次测试改变了哪些判断

前一轮 500 项测试及假模型前端/出口联调证明了组件接口、部分边界和组织方式已经接通；它们没有证明真实主脑能遵循协议，也没有证明实际中断路径能持续展示报告事实。本次 E1-6 测试在 35 项任务中写出了 29 份检查点，但这些检查点没有事实；第 30 项处理中断，第 31-35 项未执行。最终没有可导入的 Result Bundle。

与此同时，中性来源缓存确实保存了 261 个候选，包含 170 个逐字等于 IR 单元格原文的定量候选。来源理解、标准映射、Core 成果和前端之间的断层，比单个指标抽取错误更优先。缓存中仍有期间、主体、正文锚点及坐标缺陷，这些候选不能直接升级为可用事实。

因此，下一轮的首要目标是让**有限证据经过一致的协议，形成身份和来源诚实的持久成果；失败发生在正确的层，并能停止、恢复和解释**。只增加模型超时、放宽空值、补页面别名、扩大 Top N，均不能达到这个目标。

## 2. 必须保留的架构和实施边界

继续使用一份报告一个 Session、多个标准投影、唯一控制面队列、中性 SourceFact、现有 Core/Result Bundle 和现有候选数据库。程序管理来源、合同、预算、状态和版本；模型承担语义理解与适用性判断。成熟 E2-4 specialist 路径保留。

本轮不扩展 CrawlESG、企业主数据平台、Full Harvest、多机调度、标准法规改版和正式发布服务。报告中明确的主体身份属于本轮；新增公司主数据系统不属于本轮。业务候选不自动批准；数值相同不自动去重；未声明的期间、边界和 Scope 2 方法不从标准请求补造。

旧结果不可变。旧 IR 的能力声明和版本原样保留；新版本可通过显式转换消费旧证据。源解释、模型协议、引用目录和映射版本改变时，只失效受影响缓存，不能整体清空历史成果。真实模型业务复测仍由用户发起；实施方完成离线、合同、故障注入和静态验证后交付复测入口。

## 3. 下一版链路

```text
报告原件 + 冻结标准包 + 模型角色/资源预算
  → 固定 Session 和证据版本
  → 证据目录：统一真实 ID、页面定位、能力及已知结构问题
  → 来源对象/片段工作队列：表格、正文断言、正文数值分别读取
  → 类型化来源理解：明确语义轴，引用真实片段，程序展开原值
  → 逐片段写入候选与质量状态，保留成功部分
  → 按小指标族映射已合格候选，持久保存正/负/不确定裁决
  → 根据具体缺口选择补查、协议重试、局部结构修复或人工确认
  → 依赖图进行确定性计算与阻塞传播
  → 增量 Core 投影 + 可审查的阶段快照
  → 前端三视角、最终 Bundle、现有数据库候选导入
```

统一来源对象的含义不等于一次向模型发送整个对象。对象可分片读取，成功片段共享，失败片段独立恢复。一个语义结论可以引用多个真实证据片段，不能把整段陈述错误锚定到标题。

## 4. 按依赖顺序实施

### P0：建立失败样本基线及验收矩阵

**为什么先做：** 先前假模型经常直接返回符合合同的答案，隐藏了实际 prompt、引用目录、模型响应长度及中断出口问题。没有可复现基线，后续调整容易把“JSON 不报错”当成业务改善。

产出：

- 私有测试样本索引：原件 SHA、OCR/IR run 与 revision、冻结包摘要、请求、94 次模型调用、29 份检查点、执行事件和关键页视觉核对。保存路径与摘要，不复制密钥或无关主机日志。
- 通用的匿名协议回放夹具：null 标识符、正文虚构列、未知引用、无效动作枚举、重复动作、输出截断、错误修复后仍无效、Sleep/唤醒、阶段成果中断。原始中国石油数据留在私有目录；仓库测试使用最小匿名结构。
- 人工核对矩阵分别记录来源值、期间、实体、边界、方法、物理定位、映射、未披露结论、恢复状态。没有完整业务金标准之前不发布整体 precision/recall 数字。
- 验收区分离线回放与真实模型：回放只证明新系统正确处理既有坏响应；真实主脑遵循新协议的质量由下一次用户测试验证。

完成条件：本次每一类失败都有可定位的重现输入；35 项的已处理、处理中、未执行身份不混淆；审计可通过产物重新核算。P0 不将 261 个候选改成批准事实。

### P1：统一类型合同、模型协议与引用约束

**首要阻塞：** 手写 compact template、编译出的 JSON Schema、Pydantic 接收合同以及通用 prompt 对 null 的约定不一致。当前修复调用只有坏输出和错误文本，缺少原指标卡、允许引用及来源种类。修复重复错误后又被归类为缺证据。

实施：

1. 为导航、来源理解、映射建立单一类型定义；从该定义生成各 provider 协议，建立适配层等价性检查。不能独立维护三份字段含义。
2. 采用按 `tool` 区分的动作合同。检索动作只包含查询和指标引用；对象读取只包含对象/片段引用；局部修复使用其专属字段。无关字段不要求模型填空。
3. 明确 `null`、空列表、空文本及负裁决的意义。`source_id`、`metric_id`、物理引用不能为空；“不匹配”是有明确指标的负裁决，或空 `matches` 加完整覆盖记录。空值仅用于允许未知的业务语义字段。
4. 每次调用提供与任务同作用域的真实对象、指标、片段、列/单元格引用目录。支持的后端可使用约束生成；不支持时仍须先验证合同，不把方法名 `generate_structured` 当作能力验收。
5. 修复请求包含最小原任务、允许引用、失败字段、有效部分和约束。区分 JSON 语法、类型、引用、语义；引用错误不是纯格式错误。修复次数和输出规模有上限，失败后产生 `protocol_invalid`，不要求模型保留已证实非法的引用。
6. 保留合法兄弟记录，不允许一个坏引用使整对象的全部裁决消失。记录生成完成、解析通过、引用通过、语义已裁决为不同事件。

涉及：`models/structured_template.py`、`models/qwen.py`、`models/report_semantics.py`、provider adapters、`evidence/disclosure.py` 与对应合同测试。

完成条件：生成合同和接收合同对所有字段具有一致的 null/列表/枚举规则；正文负裁决和未知方法能合法返回；无效引用被阻断且有正确故障类型。不能通过让非法标识符变成可接受空值达标。真实 provider 协议成功率仍需用户复测。

### P2：统一证据身份与来源事实读取模型

依赖 P1 的稳定协议，可与 P1 的实现独立模块并行开展。

实施：

1. 阅读菜单的 ID 直接引用 canonical IR 对象；PDF 0-based index、用户可见第几页、印刷页码是独立 locator 字段。显示别名不允许成为 repair target。跨页逻辑对象显式展开为物理来源列表。
2. 来源种类至少区分表格单元格、正文断言、正文/图表中的数值。断言引用原文片段/列表成员，不引用不存在的列；正文数值由模型选择真实数值片段、单位和作用域，程序读取原文并展开，不能要求其必须来自表格 cells。
3. 中性身份使用有定义的主轴：期间、主体/角色、边界、测量类型、Scope、方法等。开放字段进入专门扩展空间，避免把 `2021`、`2022` 等表头文本当字段名，也避免把同行其他年度数值塞入某单元格身份。
4. 每个身份值保留支持它的表头/正文引用。未知身份明确标记并保留缺口。报告主体可引用原报告说明与标题，不能从文件名推断，更不能从标准固定值补造。
5. 修正检索阅读层的表头继承规则：章节分隔行不应跨章节挂到不相干数据行。本次 canonical IR 的温室气体年度表头正确，错误发生在 Evidence Inventory 把首个合并分区行当作全表头并向下传播；不能误修原 IR。真实有损表结构才走 IR 修订；模型误用已有列则留在协议层处理。
6. 定性陈述支持多片段证据；“标题存在”只证明对象存在，不证明整段陈述就在标题框内。源事实质量必须记录细粒度引用是否可核对、bbox 缺失及身份缺失。
7. 数值与单位由 IR/确切文本片段展开，模型生成的定量解释句不参与数量与单位转换。明确、可验证的单位规范化由程序执行，原值及原单位永远保留。
8. 表头、章节分区、空白和纯结构行具有独立的已读角色，不要求它们必须产生事实才可结束。上下文行与本次需解释的行显式区分；传入图片的视觉范围与目标片段匹配，防止只剩四个结构行时又诱导模型重抄整表。

涉及：`evidence/regions.py` 阅读视图、`ir/loader.py`、`evidence/inventory.py`、`report_facts.py`、`models/source_facts.py`、`models/report_semantics.py` 及源质量合同。

完成条件：表格五年度能形成五个明确期间的候选；正文中的真实数值可保留；每项来源能定位到真实对象，页面跳转与修复选择一致；正文无列不会触发协议失败。具体 ESRS 是否匹配留给映射层。

### P3：将失败与证据缺口拆开，形成有进展的报告工作队列

依赖 P1、P2。当前 topic 小循环已经存在，但协议错误进入普通 `context` gap、不同主题重复触发同类失败、完整对象完成标志和待处理片段混在一起。需要完善原有 Session 内的调度，不新增平行 Agent 系统。

实施：

- 建立分层故障：传输/主机、生成协议、无效引用、真实 IR 结构、语义不确定、证据未覆盖、标准不适用/未披露、派生依赖缺失。每类规定允许的下一步。
- 故障账本按 Session/topic/attempt/对象片段归属，不扫描全历史动作仅凭 object key 重附当前失败。本次 dp25 的主题误带入 dp08 的缺口，必须成为跨主题隔离回放用例。
- IR repair 只接受有结构问题证据的请求，例如确切表头缺失、单元格错位、跨页连接冲突；模型虚构列、JSON 错误、请求超时不能升级为 IR repair。
- 用对象片段、解释版本、证据版本、映射指标族维护工作状态。成功片段独立保存，已解决缺口退出 active 集合，失败片段保留因果链；不得因历史错误仍在列表里永久降低全部兄弟结果。
- 区分物理原值已读取与语义身份已完成。已经标为 processed 的数值行仍可根据具体期间/主体缺口执行有界语义重读，不能只允许读取 pending 行，从而永久冻结首次错误身份。
- 负匹配和合法的不确定裁决同样持久保存；跨主题可以复用来源理解，标准映射按冻结包摘要单独缓存。整对象不 complete 不能使正确片段失去复用资格。
- 对重复协议失败建立报告级限制；同一输入和失败签名不应在多个 topic 中无限重试。模型下一步必须改变证据、任务作用域或修复条件才算进展。
- 检索覆盖记录哪些证据角色已访问、哪些分支未检查。只有检索充分且协议正常时才能形成限定范围的未找到结论。未执行不是未披露。
- 分别记录检索命中、对象菜单选择、实际阅读三个阶段。相关行排第一但主逻辑表没进首次菜单，属于对象选择问题；不能靠提高检索排名掩盖。目录/GRI 索引应导航到正文，不反复当业务事实读取；术语仅作定义上下文。
- 派生依赖图分别表达来源可用、标准映射可用、口径对齐和计算可用。依赖不足产生 blocked 及具体原因；不得用 Scope 1+2 合计替代单独 Scope，或替代含 Scope 3 的总量。直接披露强度仍可以走合法证据分支。

涉及：`evidence/disclosure.py`、`contracts.py`、`report_session.py`、`workflow.py`、checkpoint/source cache 和 `results/derivation.py`。

完成条件：一次协议失败只影响对应片段/映射；正确兄弟来源、裁决和成果可消费；重复失败能有界停止；未覆盖、失败、未披露、未执行在机器状态及页面文案中都可区分。

### P4：从逐调用超时升级为报告级资源生命周期

依赖 P1 的调用/故障合同，P3 的工作状态。

实施：

1. 将输入规模、预估输出规模、模型调用数、修复占比、持续无进展次数和总预算纳入 Session 调度。Top N、每主题 action 数和单次 600 秒只是其中部分边界。
2. 按 token/输出合同分片，而非只按 12 行分片。小指标族映射相关候选，必要身份和脚注保留；不反复带入全部历史错误和无关大表。输入和输出增长触及上限时拆任务，不靠盲目增大 max_tokens。
3. 正确记录完成原因。截断输出先归为 generation_incomplete 并缩小任务；不把缺半截 JSON 当作“格式润色”任务再次发送同样巨量响应。
4. 由唯一 worker 管理模型加载、释放、embedding 切换、资源占用与主机活跃生命周期。macOS 使用可清理的系统电源声明管理任务执行期间的自动空闲睡眠；用户强制睡眠仍可发生，必须有暂停/唤醒策略。
5. 分别记录墙钟时间、进程活跃时间及检测到的 suspend 区间。说明期限采用哪一种时间语义；唤醒后先处理过期调用和持久化状态，再决定恢复。主机睡眠期间本机 watchdog 无法执行，不能声称绝对实时硬截止。
6. 完成、取消、异常、worker 崩溃都能释放模型、执行槽和电源声明。前端显示最近进展和阻塞阶段，避免把陈旧 token 心跳当作仍在有效推理。

涉及：MLX runtime、`storage/execution_supervisor.py`、控制面 worker/execution slot、事件合同与运行视图。资源策略按平台适配，不污染 ESG 标准包。

完成条件：规模过大/输出截断/主机挂起的故障注入均产生清楚、可恢复的状态；同一故障修复调用有界；资源在各退出路径清理。真实时延预算由新一次用户测试测量，不凭现有离线速度承诺耗时。

### P5：接通增量成果、统一状态与产品可见性

依赖 P2、P3；与 P4 后期可以并行。

当前 `ReportSession.detail()` 依赖 child manifest 是否存在判断成果；来源缓存 API 已能读到候选，报告事实页在有 child job 时也具备入口，不能称其完全不可见。旧标准成果 inspection 仍依赖 Bundle，因而本次无有效投影可展示。问题在于 `not_evaluated` 与已存在候选之间缺少阶段/质量表达，报告视图未清楚展示 incomplete/gaps，部分期间/Scope 又因字段读取不一致为空。此处结论来自静态调用链核对，未冒充实际浏览器验收。

实施：

- 每个来源片段写出候选、质量状态和证据；每个裁决写出标准映射；每个满足合同的映射写出 Core 投影。以实际持久成果和质量计算 result 状态，不以最终 manifest 是否存在代替。
- 发布版本化阶段快照，最终 Bundle 仍走现有 exporter。中断也可导出合规的 partial：有效记录、未完成清单、来源范围和失败原因同时存在。只有候选、没有可用 Core 的快照要明确表达，不能伪装为可入库成果。
- 统一 Session/child/queue/outcome 的因果故障和双轴状态。29/35 表示处理进度，不表示 29 个有效结果；展示候选数、有效映射数、可用记录数及未执行数。
- 报告事实视图直接消费 Session 的阶段事实合同；标准覆盖视图消费裁决与任务状态；证据视图消费同一来源定位。任务未完成时这些入口仍可用。
- 对空事实集合的 Guard/source/contract 检查标明检查对象和数量。结构合同通过仅表示任务记录合法；不能以绿色“来源通过”暗示已经核验了业务事实。
- 待处理动作根据故障类型生成：协议失败展示重试或引擎配置，真实结构缺陷展示局部修复，缺少身份展示确认，依赖不足展示阻塞证据。普通用户不需分析原始堆栈。
- 候选数据库继续独立审核来源和映射。只有合规 partial/Core 才进入当前 importer；未审核来源缓存不能绕过审核自动落入正式事实。

涉及：`report_session.py`、`workflow.py`、`results/exporter.py`、inspection/service、控制面 outcomes、前端 `sessions.js`/`results.js`/`status.js`/`targeted.js` 与已有数据库 importer。

## 6. 明确不采用的修补方式

- 不为中国石油、某页码、某年度或某指标写专用 if 分支。
