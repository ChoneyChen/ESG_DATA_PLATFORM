## 1. 对需求的理解与产品方向

用户希望把项目重心转向可用的数据产品：先把少量有价值的披露准确、规范、可追溯地纳入数据库，形成独立的企业展示与同行比较平台，再分批扩充指标。完整 ESRS 目录负责保证覆盖路线有据可查；完整提取能力不再作为第一版上线的前置条件。

应当用三个独立问题组织产品：这个标准要求什么？这个平台希望展示什么通用概念？这次报告只需要提取什么？标准条款、通用指标和执行范围分别回答这三个问题，不能用同一组字段混合表达。

第一版成功标准应是：用户能找到企业和指标，读懂数值、单位和口径，定位报告证据，对符合比较条件的企业做比较，下载一个有数据版本的结果。仅增加条款非空数量、增加提取记录或完成一次长任务，不能说明数据平台已经可用。

此前中国石油测试揭示的原值、身份、证据、协议、状态和阶段成果问题仍然有价值。此次产品收敛减少要执行的范围，不降低已选指标的证据和身份要求。原值读对但主体、年份、排放方法或边界缺失的数据，可保留候选与来源展示资格，不能被自动认定为可横向比较的正式观测。

## 3. 如何选重点指标

建议采用有理由的分层选择，而不是伪精确的百分制打分。选择依据是：与企业环境社会影响直接相关；在目标企业报告中有机会获得；定义可以稳定建模；满足比较条件时有实际分析价值；现有工程能够以有限成本形成证据完整的结果。

这五个依据中，真实披露率和提取成本尚未在足够多真实报告上测量。因此以下是产品建议，不是声称经过统计验证的最优排名。应通过首批 5—10 家企业、各 2—3 个报告期的试点修订范围，不能据单家报告的披露习惯决定整个指标字典。

分层建议：

- **身份与方法支撑**：主体、期间、合并范围、运营或价值链边界、方法、单位、证据。按所选指标需要读取，不要求全套叙述条款输出。
- **核心指标 core**：建议 V1 公开展示的 16 个指标；符合严格比较条件的观测才进入比较结果。
- **行业指标 sector**：污染物、敏感场址、材料、投诉等，通过行业配置选取。
- **必要叙述 context**：政策、目标、申诉和补救等结构化主张，用于理解和风险展示。
- **完整扩展 extended**：保留在目录，按价值和验收情况逐批建立成熟包。

产品层级与法定披露义务相互独立。例如 E3-4_11 的取水量可以是产品核心指标，同时保留原表对该条款的 May 属性。现有 `anchor/detail/context/derived/presentation` 是条款语义角色，不代表产品优先级；不得通过把条款改成 anchor、mandatory 或删除 detail 来实现产品收敛。

对于中国石油这样可能披露“范围1＋2合计”的报告，应保留独立的 `ghg.scope1_2_combined_reported` 候选概念和明确的范围标签。它不满足上述范围1或范围2的条款定义时，不进入这些列，也不通过减法拆造。该补充概念是今后企业特有披露的规范映射示例，不能伪装成原表新增编号。

## 6. 已有实现与需要新增的内容

本轮核对了项目事实入口、系统重塑方案相关架构、标准包合同、ReportSession 选择与依赖处理代码、数据库迁移和数据库说明。可复用的现有基础是：

- 一份报告一个 Session，多标准投影共享中性来源事实；请求支持 `metric_ids`。
- 显式派生依赖闭包，内部依赖与所选输出分别保存；目前主要解决已声明计算依赖，尚无完整产品 profile 编译。
- 源事实、标准映射和结果 Core 分离，Bundle / JSONL 可供候选导入。
- E1-5、E1-6、E2-4 有 draft 2.0.0 包，尚未完成全部真实报告准确性验收。
- 结果库已采用 PostgreSQL SQL，含规范概念、单位、期间、维度、原值、证据、映射、导入批次和审核记录。
- 事实审核与映射审核独立；尚无正式发布数据集服务或独立数据平台 HTTP/UI。

因此“格式不是数据库格式”需要更准确地表述：JSONL/Bundle 本身是合适的交换格式，现有库已经有关系结构。欠缺的是经过审核的规范概念和身份解析、正式发布规则、可比较观测、发布版本和产品 API。应继续使用现有候选导入器，通过版本化适配器连接正式库，不再创造第二套互不相通的事实文件。

## 7. 数据库与技术栈选择

**建议：正式主数据库采用稳定版 PostgreSQL，数据库语言采用 PostgreSQL SQL。** 当前迁移使用 17+ 兼容语法；部署时选择经过兼容和负载验证的受支持稳定版本，不因研究文档自动升级运行时。

本项目主要负载是有审核流程的事实写入、企业—期间—指标筛选、证据关联、版本和冲突追踪、有限同行比较。PostgreSQL 的事务、主外键、唯一约束、类型化列和 SQL 联接与这个负载匹配，也延续已有投资。这里的“适合”是架构判断，尚无本项目生产规模的性能实测，不能称其为所有场景最快的数据库。

原披露量与金额使用精确 `numeric`，人数和件数使用合适整数，时间用 `date`/`timestamptz`，标识用 UUID/稳定文本码。原始数值不通过一个固定小数位列过早截断；字典指定有效精度和展示位数，计算结果按版本化规则存储。禁止把 NaN/Infinity 当成真实观测。API 对精确 decimal 返回字符串及单位元数据，浏览器仅在绘图时做展示转换。[PostgreSQL 数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)。

高频筛选字段采用类型化关系列，例如主体、期间、指标、方法、边界和发布版本。可扩展维度及方法细节可以使用规范维度表与 JSONB；不可把所有数据存为任意 JSON。JSONB 可索引，但不会保留所有原始文本格式，PDF和原JSONL仍按不可变资产保存。[PostgreSQL JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)、[约束](https://www.postgresql.org/docs/current/ddl-constraints.html)。

| 组成 | 建议 | 理由与边界 |
|---|---|---|
| 正式主库 | PostgreSQL | 审核、版本、证据与规范观测统一事务管理 |
| 本地开发 | 现有 PGlite | 保留开发便利；不以浏览器或单用户运行时承担生产服务 |
| 业务服务 | Python FastAPI，迁移采用既有SQL体系或后续统一Alembic登记 | 复用现有Python/Pydantic能力，OpenAPI合同统一 |
| 独立前端 | React、TypeScript、Vite | 延续团队当前技术；独立路由、构建和数据API |
| 原始资产 | 当前本地不可变目录，后续对象存储 | PDF、IR与Bundle按hash引用，数据库保存元数据 |
| 后续批量分析 | PostgreSQL导出Parquet，按需DuckDB | 研究快照和离线分析；无须首版增加第二个在线权威数据库 |
| 首版暂缓 | 分布式仓库、Kafka、向量数据库、复杂微服务 | 当前无相应规模和业务必要性；后续用实测触发 |

DuckDB 可直接查询和导出 Parquet，适合后续冻结数据集的本地研究与批量分析。[DuckDB Parquet文档](https://duckdb.org/docs/current/data/parquet/overview)。PGlite 延续目前开发用途，正式服务使用服务器PostgreSQL。[PGlite开发说明](https://pglite.dev/docs/)。

FastAPI 自动生成 OpenAPI/JSON Schema，可以作为前后端模型的统一来源。[FastAPI 文档](https://fastapi.tiangolo.com/tutorial/first-steps/)。React 官方提供从零搭建应用的选择说明，Vite提供开发和构建能力；这里选择独立 SPA 是基于目前内部展示、证据查看与筛选需求，尚无必须服务端渲染的理由。[React](https://react.dev/learn/creating-a-react-app)、[Vite](https://vite.dev/guide/)。

## 8. 科学数据结构：事实、观测与比较集合

应明确两种粒度。

**报告事实**保存报告到底说了什么。现有 `esg_disclosures` 和其数值、维度、来源、关系、标准映射表继续负责这一层。一份新报告可能再次披露同一年度或重述旧值，多个来源可以冲突，不能用企业＋年份＋指标作事实唯一键。

**规范观测**表示在明确主体、期间和测量条件下，一个经过审核的通用指标值。它引用一个或多个被批准的报告事实及其审核决定，不覆盖原事实。比较 API 使用带比较合同的观测集合。

推荐逻辑粒度：

```text
entity_id
  + metric_definition_version
  + actual_period / observation_date
  + reporting_boundary_id
  + measurement_method
  + population / geography / activity / analyte / breakdown
  + value_role
  + observation_revision
```

单位转换后的规范单位由指标定义规定；单位转换不会消除边界和方法差异。未知维度必须是未知，不能借默认空字符串与另一个未知观测形成“口径相同”。

| 数据对象 | 主要字段 | 与当前系统关系 |
|---|---|---|
| 企业和报告注册 | 稳定主体ID、法定名称、集团/上市主体、外部ID、行业分类版本、报告版本/PDFhash | 独立PlatESG注册模块；通过已有organization_ref关联上游，不修改CrawlESG |
| 指标定义版本 | 概念码、数量种类、定义、规范单位、必需维度、可加性、比较合同、来源标准映射 | 扩展现有canonical_concepts，不仅使用名称同义词 |
| 期间 | 开始、结束、时点、年化资格、财年标签 | 不能用报告文件名年份代替披露期间 |
| 测量上下文 | 合并/运营/价值链边界、方法、统计人群、活动、区域、物种等 | 高频字段类型化，长尾保留规范维度 |
| 原始事实与证据 | 源值/单位/原文、表行列/正文片段、IR版本、页码、证据hash | 复用现有表和固定资产 |
| 规范观测 | 值类型、精确值或上下界、规范单位、context、来源事实ID、修订关系 | 新增版本化投影，不能复制为新的原始事实 |
| 审核与发布 | 对象及版本、审核人/理由、概念映射决定、发布日期、数据集版本、撤回/替代 | 当前review_decisions向发布接续 |
| 缺失及覆盖 | 所选指标、提取状态、已读范围、缺口类型、适用判断依据 | 无值也有可解释状态；不得插入0 |

建议通过下一编号迁移新增 `metric_definition_versions`、`measurement_contexts`、`curated_observations`、`publication_events`、`publication_batches`、`outbox_events` 和 `metric_coverage` 等逻辑对象，最终物理表名以实施设计评审为准。企业主数据由未来 `PlatESG` 注册模块管理自己的 schema/迁移；结果库继续只改 `esg` / `esg_api`，不突破现有模块边界。

正式观测的业务身份先构造规范上下文，再生成稳定身份摘要。摘要不能仅是数值hash，也不能代替可读字段。多个批准来源支持同一观测时建立来源关联；存在未裁决冲突时停止首选值发布。重述记录保留 `supersedes`，发布集支持 `as_of` 读取，既能看到现在采用的值，也能复现过去的数据集。

不可加的比率不直接平均；需要合并时重新汇总匹配的分子与分母。期末员工数不能跨年度求和。集团和子公司不在同一汇总范围重复相加。总排放与Scope明细不同时累加；地点法和市场法是两种总量方法，不是可相加的组成。

## 9. 比较资格是独立合同

事实审核通过、符合某条款、正式发布、可用于某种比较，是不同状态。应分别记录 `fact_review_status`、`mapping_review_status`、`publication_status`、`comparison_eligibility`，而不是扩充一个万能quality_status。一个真实、已审核、正式可展示的观测，也可能只允许带条件地阅读，不能加入严格排名。

比较请求至少验证：

1. 指标定义版本相同或存在经过批准的等价映射。
2. 期间长度、实际/目标/基准属性及统计时点符合请求合同。
3. 主体类型和报告边界满足可比范围。
4. 单位转换合法，币种和货币基准符合请求约定。
5. 排放方法、GWP、污染物、人口、统计规则或分母符合指标特定条件。
6. 不存在未裁决值冲突，来源质量符合发布策略。

输出资格可以为 `comparable`、`conditional`、`not_comparable`，附具体原因码，如 `scope2_method_unknown`、`employee_basis_differs`、`currency_basis_differs`、`boundary_unknown`。这是针对一个比较合同的结果，不能写成某企业“不可比较”的永久标签。

常见必须阻断的合并：范围1＋2合计映射成范围1；取水当耗水；处置量当产生量；FTE当人头数；LTIFR当所有可记录事故率；内控处分数当法律定罪数；中国石油天然气集团当中国石油上市公司；运营收入当未核实的净收入分母。

货币量首版默认原币种筛选和展示。确需汇率转换，记录来源、平均/期末汇率、日期及规则版本；跨期分析还需要明确名义/不变价政策。产品不能默认用今日汇率转换历史收入并计算排放强度。

缺失状态至少区分 `not_selected`、`not_extracted`、`source_unreadable`、`not_disclosed_in_reviewed_scope`、`not_applicable`、`review_required`。其中“未披露”只能针对经过确认的已读范围，不能由预算用完推导全报告未披露；不适用需要依据。显式0、缺失、低于检测限和范围值分别保存。

## 10. 提取后审核、自动正式入库的连接

建议在业务语言中明确“候选入库”和“正式发布”。抽取结果可以自动进入审核库，只有满足批准和发布条件的基础指标才自动进入正式数据集。

```mermaid
flowchart LR
  A[用户选择基础指标配置] --> B[冻结报告与标准包版本]
  B --> C[定向提取与有限补查]
  C --> D[合同通过的Core和来源证据]
  D --> E[版本化候选导入适配器]
  E --> F[候选库]
  F --> G[审核事实、主体、口径和映射]
  G --> H[批准决定与待发布事件同事务保存]
  H --> I[发布处理器检查指标范围和比较合同]
  I --> J[带版本的正式观测与覆盖状态]
  J --> K[独立展示平台与数据API]
```

具体步骤：

1. **任务入口**选择profile，展示输出指标、所需内部依赖和报告主体确认。冻结PDF/IRhash、profilehash、指标字典版本、标准包版本和规则版本。
2. **提取**仍使用现有 Session 和共享来源，停止条件针对所选指标和必需上下文，不把整个标准主题的阅读完成作为前置条件。允许partial成果逐项候选导入，保留未完成指标的覆盖状态。
3. **适配器校验**读取正式Core/manifest和实际证据，保留原始事实，拒绝把未经映射和验证的模型候选直接转正式数值。当前零Core历史检查点不能自动变成已批准观测。
4. **候选入库**按批次和不可变来源身份幂等。重复批次返回同一结果；同一来源身份解释漂移按既有机制拒绝或显式新修订，不能静默覆盖。
5. **审核工作台**一次展示原页/片段、原值、单位换算、主体、期间、方法和概念映射。事实批准与映射批准可以同屏完成，但保存不同决定。批准对象必须指向确定修订，后续重提取不能沿用旧批准。
6. **批准触发**在同一个PostgreSQL事务内保存审核决定和outbox事件。事件仅表示“待发布”，不表示发布已完成。
7. **发布处理器**确认profile许可、规范概念映射批准、源事实批准、必需身份完整、规范化成功、冲突已裁决和策略允许展示。对比较结果再执行专门的比较资格检查。
8. **发布事务**写入正式观测/来源关联/数据集版本和事件处理状态；中断后可重试，以事件ID及观测修订唯一约束保证逻辑幂等。处理最新审核状态，撤回后不允许迟到的批准事件重新发布旧记录。
9. **读取端**只读正式发布投影；显示发布版本和时间。已审核未发布状态在审核台可见，不能被现有“approved即API可读”视图不加区分地作为正式平台入口。

审批和通知的双写问题可用事务outbox解决。官方模式也要求消费者处理重复投递，因此这里承诺可重试和幂等，不把整个跨服务链路宣传成天然exactly-once。该原则可在本地PostgreSQL实现，不要求使用AWS服务。[AWS 事务outbox模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

同一数据库内首版采用事务＋outbox表＋轻量发布处理器即可。该处理器不运行模型，不另建OCR/定向抽取重负载队列。原统一Worker控制面继续负责重任务。

发布事件建议至少包括 `event_id`、`event_type`、`review_revision`、`fact_ids`、`mapping_decision_ids`、`metric_version`、`profile_version`、`occurred_at` 和 `idempotency_key`。机器接口数值采用decimal字符串，原始来源通过ID/hash引用。导入失败、审核退回和发布失败各有独立状态及原因。

## 11. 标准包与定向提取的分层更新

建议形成四种独立、互相引用的版本化材料。

| 材料 | 负责什么 | 不混入什么 |
|---|---|---|
| Standard Catalog | 原标准版本、DR、DP、原文位置、条件、共用要求引用、条款关系 | 不以产品优先级删改规范要求 |
| Metric Dictionary | 通用概念、规范单位、事实粒度、身份轴、可加性、比较与发布合同 | 不把ESRS编号当唯一通用概念码 |
| Semantic Package | 语义任务卡、单位与维度、输入/输出合同、易混项、声明依赖、派生规则 | 不加入模型名、topK和临时运行预算 |
| Extraction Profile | 产品core/行业/研究范围、输出清单、上下文需求、允许发布概念、版本hash | 不复制一份缩水且失去来源的标准包 |

现有格式 `2.0` 的严格合同只接受定义过的字段。实施时新增profile合同及编译器，并为确需扩展的语义字段设计兼容版本；不能往YAML随意加 `priority` 后宣称系统已支持。发布目录中的“catalogued”、语义“draft”、测试“validated”、业务“approved”分别记录。完整目录存在，不意味着所有条款已有成熟提取包。

profile解析后形成三份集合：

- `output_metrics`：用户要看到的指标，唯一决定成果覆盖分母。
- `required_context`：主体、期间、单位、边界和方法证据，以及确需计算时的内部操作数。
- `contrast_definitions`：只供辨别的易混概念，如取水/耗水、地点法/市场法，不激活其全部提取任务。

只有声明的计算依赖和必需上下文进入执行闭包；展示关系、分解树、共同主题或一个泛化anchor不会让全主题自动入选。读取某张表以获得所选值时可以保存中性来源，未选择的条款不因此变成待完成输出。

首批profile建议：`core_esg_v1`（16个目标概念）、`core_energy_ghg_alpha`（现有包的5个核心概念）、`sector_pollution_basic`（根据行业选择SO2/NOx/COD等观测）、`full_catalog_research`（后续需要时显式选择，默认关闭）。行业profile里指定污染物词典和介质，不为每个污染物编写专用后端路径。

标准包的内部章节建议统一为：来源和适用条件；主题与条款树；输出观测卡；身份和方法要求；单位归一；明确关系和计算依赖；易混概念；证据要求；缺失状态与验收样例。核心、明细、方法、派生、呈现的角色仍保留，增加独立产品层级引用。

例：只选范围1、范围2地点法、范围2市场法时，执行这三项与必要排放方法/边界；不自动激活范围3、强度、碳信用、内部碳价或财务影响。若只选可再生能源占比，直接披露优先；必要且合同允许时读取同范围的可再生及总能耗作为内部操作数，不能要求煤/油/气每种组成都有值才算任务完成。

提取预算由运行配置控制，按目标规模及证据质量设置总预算和单项补查上限。预算用尽返回可审核成果与明确缺口。置信分数不能代替审核；首版不因分数高就自动批准。

## 12. 独立展示前端

推荐新增独立 `PlatESG` 模块，拥有自己的前端构建、读API和注册/发布应用服务。可复用现有结果表、单位显示和证据查看组件，但不让展示页读取本机任务目录、控制抽取Worker或依赖某个任务必须completed。

第一版只需要五类页面：

1. **企业目录**：主体全名、集团/单体、行业、已发布报告期、指标覆盖。搜索通过稳定ID解析企业别名。
2. **企业详情**：16项基础指标按E/S/G组织，年度趋势、原单位/规范单位、口径与缺失原因。多种范围/方法不能合并成一条折线。
3. **指标浏览**：定义、单位、来源标准、适用行业、报告企业、期间及比较限制。
4. **同行比较**：选择企业、指标和报告期；返回合格集合与被排除原因；默认不跨行业做综合排名。首版只实现数据表与简单趋势，不建设综合ESG评分。
5. **事实证据详情**：报告版本、原值、片段和页码、方法、审核/发布时间、数据集版本及更正历史。

审核工作台是写入业务模块，作为内部页面单独授权；公开展示与比较API只读。浏览者无需理解IR、模型或包编译技术信息；证据页保留足以判断数值含义的来源和口径。

可见状态使用清晰文案：“原文未给出方法”“本次未提取”“已审核，等待发布”“该口径不能与当前选择比较”。未知不用0或空白代替，不用深色绿勾表示已完成所有质量条件。

## 13. API合同与分析扩展

API从V1就公开规范身份与版本，不把内部文件名作为主键。

| API建议 | 首版职责 |
|---|---|
| `GET /v1/entities` | 企业检索、行业筛选、主体关系 |
| `GET /v1/metrics` | 指标定义版本、单位、必需维度、比较合同 |
| `GET /v1/observations` | 按企业、期间、指标、方法、范围和dataset_version筛选 |
| `GET /v1/observations/{id}` | 观测、来源、审核/发布状态、修订关系 |
| `GET /v1/coverage` | 所选范围、缺失原因及可用期数 |
| `POST /v1/comparisons` | 执行比较合同，返回资格/排除原因和观测 |
| `GET /v1/datasets/{version}` | 发布快照、字典版本、来源摘要及导出入口 |
| `POST /internal/v1/import-batches` | 内部候选导入，复用现有导入器 |
| `POST /internal/v1/reviews` | 指定修订的事实与映射审核决定 |

筛选响应包含 `dataset_version`、`metric_definition_version`、`comparison_contract_version`、`as_of` 和稳定分页游标；允许同一请求固定数据集，避免分页过程中结果漂移。数值为精确decimal字符串，带单位、值类型和精度；范围或低于检测限值不能变为点估计。

导出先提供CSV/JSON，随后Parquet分析快照，包含schema版本、列定义、缺失值规则、来源报告、数据许可/访问范围和数据版本。后续统计与聚合API必须引用同一比较合同，不另起一套“宽松”口径。数据许可证需针对项目实际来源和提供方式确定，不能仅因网上可下载就写成可无限再分发。

首版索引围绕真实查询：已发布观测的实体＋指标＋期间；指标＋期间＋行业；来源事实ID和发布版本。先用普通视图、参数化SQL和适量索引；性能测试后再决定缓存、物化视图和分区。物化快照必须显示刷新时间，不能伪装成即时数据。[PostgreSQL 物化视图](https://www.postgresql.org/docs/current/rules-materializedviews.html)。

## 14. 全部数据点的标准包建设路线

完整目录现在可导入，不表示现在就编译运行所有数据点。推荐“完整注册、分批成熟、配置选择”。配套建设表逐分组列出全部原始ID、重点ID和阶段，作为后续工作底单，不声称每组已有通过验收的任务卡。

包建设按以下模板覆盖全集：

- **数值观测模板**：数量种类、单位、期间、主体、边界、方法与聚合规则。
- **维度/表格模板**：表格整体是来源容器，数据点是输出观测；显式关系和维度词典，禁止总量与明细重复入账。
- **类别/布尔模板**：肯定、否定、未知、未适用分别建模，处理原表否定表述。
- **定性主张模板**：原子陈述、主体、动作/状态、对象、期间和证据，不假造可计算数字。
- **政策—行动—目标模板**：政策对象、责任、行动、资金、目标及基准形成关联；MDR共享，主题仅投影。
- **财务影响/情景模板**：金额上下界、币种、时域、情景、估计与假设，不能与历史实际量混用。

每个条款成熟过程：登记原文→区分观测/引用/结构/方法→映射通用概念或保留标准专有概念→定义身份轴和证据→声明依赖→建立正常/易混/缺失样例→编译检查→离线回放→有限真实业务验收→批准相应profile发布。目录编号只负责定位，不能从英文名称自动生成一份号称成熟的标准包。

优先建设顺序：E1-5/E1-6现有包核心子集→E3-4/E5-5→S1-6/S1-14→G1-4→E2-4行业配置→E1目标与范围3/强度、S1多样性/培训→E4场址、材料、S2/S3/S4定性/事件→其余财务影响、复杂情景和更细分项。MDR模板及身份/方法合同从第一阶段就同步建设。

## 15. 实施安排与验收门槛

本计划使用阶段出口控制推进，不以未经估算的工期承诺进度。

| 阶段 | 工程工作 | 可评审成果与出口 |
|---|---|---|
| A 范围与合同 | 批准16项候选字典；定义主体、边界、方法、状态；profile合同和编译预览 | 版本化字典、原条款映射、必需身份/比较规则；只选一个指标不会扩成全主题 |
| B 首条发布流程 | 用现有E1包5项核心数据，接候选导入、审核、发布事务和读API | 一个可复现的小数据集；同批重试不重复、撤回有效、错主体/方法拒绝比较 |
| C 独立展示 | 企业、指标、事实证据与覆盖页面；基础数据表比较 | 平台完全从正式发布API读取；证据可定位，未知和未披露区分 |
| D 扩展16项 | 新建水、废弃物、员工、安全、治理子包；复用统一模板 | 5—10家、2—3期试点；发布指标逐项达到质量门槛，无需每家填满16项 |
| E 行业与分析 | E2污染物、材料、场址、投诉等；导出和简单统计 | 比较条件明确，来源/规则/版本可复现；再按负载决定分析设施 |
| F 全集成熟 | 逐组任务卡、离线/真实验收和业务批准 | 原目录每条均有明确建设状态，逐批增加profile能力 |

建议的初始质量门槛：所有正式记录100%具有可定位来源、确定的主体/期间/单位和必要口径；进入严格比较的记录100%通过该指标比较合同；上线16项每项做独立人工金标准核对，报告值、身份和映射精确率目标≥98%，关键主体/方法错配为0。这里是建议验收标准，不是已有测得的准确率。首批样本过小必须报告分母及错误数，不能用几条全对声称已达总体98%。召回率单独按已披露且人工确认适用的目标观测计算，不用所有ESRS条款作分母。

必要故障场景：真实协议坏输出；方法未知；正文数值与表格重复；跨期重述；集团/子公司同名；合计与明细；币种不同；任务中断的partial；审核修订后旧事件迟到；发布处理中断重试；批准事实但映射未批准；已发布后撤回；未读完整报告却被标为未披露。继承上一轮修复回放，专门验证新发布合同，而不是再次堆积理想假响应测试。

不为第一版追加全报告Full Harvest要求、每个条款专用代码、全量叙述评分、复杂分布式基础设施或先跑完所有ESRS指标的验收依赖。能力扩张应由新数据产品需求和真实质量证据驱动。
