# 阶段 11：条款编辑器

日期：2026-10-28  
范围：`ExtractESG/standards`（草稿存储与校验）、定向提取 API、文档 API 代理、Console 标准中心。

## 1. 目标与边界

编辑一条条款不应该要求改代码，也不应该直接改动不可变包。阶段 11 把编辑做成**草稿**：

```text
不可变包（现有任务与发布读取）
   └─ 条款目录 clauses/…（生成）
        └─ 草稿 clause-drafts/<id>/（作者编辑，五个文件 + manifest）
             └─（包构建）→ 新包版本 → 试提取 → 真实验收 → 可发布
```

**草稿不会自动进入提取或发布。** 这一条是刻意的：阶段 5 的门禁要求条款通过真实验收才能标为可发布，
而验收必须绑定确定的合同摘要；草稿的摘要随每次保存变化。

## 2. 草稿内容与不变量

- 五个文件：`clause / retrieval / evidence / acceptance / provenance`，与条款目录同构；
- 可编辑字段：正向定义、易混概念、排除条件、输出口径（期间/主体/值角色/聚合/方法/必需）、
  检索正/负词、证据要求、验收样例；
- 保存时重新计算 `contract_digest`（内容寻址），并写回 `provenance`；
- 并发保护：保存必须带打开时的摘要，摘要不符即拒绝；
- 单位维度必须与父条款一致，否则拒绝（不同物理量不能借用同一条款身份）；
- 口径只能用受控枚举，自由文本直接拒绝。

## 3. 校验结果

```text
errors    自由文本口径、缺少必需口径、数值条款缺单位、单位维度与父条款不一致
warnings  证据要求里没有 value、没有验收样例（说明无法进入可发布）
```

真实样例（E1-5_01 端到端）：创建 → 校验通过 → 修改检索词 → 摘要由 `befae8fe…` 变为 `29a0ade6…` →
重新校验通过 → 丢弃后目录清空。全程未改动 `clauses/` 与任何包。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/clause-drafts` | 草稿清单 |
| POST | `/api/clause-drafts` | 从条款目录复制出草稿（需作者与修改说明） |
| GET | `/api/clause-drafts/{id}` | 五个文件 + manifest |
| PUT | `/api/clause-drafts/{id}` | 保存编辑（带期望摘要） |
| POST | `/api/clause-drafts/{id}/validate` | 重新校验 |
| DELETE | `/api/clause-drafts/{id}` | 丢弃 |
| GET/POST/PUT/DELETE | `/api/pipeline/clause-drafts…` | 控制台同源代理 |

## 5. Console

标准中心新增“条款编辑与草稿”：

- 选择条款 → 填写作者与修改说明 → 新建草稿；
- 结构化编辑：正向定义、易混概念、排除条件、口径表（下拉枚举 + 增删）、检索词、证据要求、验收样例；
- 保存 / 重新校验 / 丢弃；显示校验错误与提示、当前摘要；
- 本包草稿列表，点击继续编辑。

页面不做自由 JSON 编辑，也不接受未注册的算子。

## 7. 草稿如何进入链路（已闭环）

```bash
cd ExtractESG/standards
PYTHONPATH=src python scripts/build_clause_catalog.py --include-drafts
```

- 只有 `status=validated` 的草稿会被应用；应用后重算条款摘要，`catalog.json` 记录
  `drafts_applied` 列表，任何人都能看到这一版目录里含哪些草稿；
- 不加 `--include-drafts` 时目录与不可变包完全一致（`--check` 为 0 stale）；
- 目录更新后可跑试点提取；验收仍走阶段 5 的账本，绑定新的合同摘要。

真实闭环验证（E1-5_01）：

| 步骤 | 结果 |
|---|---|
| 新建草稿 | `draft-db…`，校验通过，摘要 `befae8fe…` |
| 保存排除条件「不含车辆燃料」 | 摘要变为草稿新值，状态 validated |
| `build_clause_catalog.py --include-drafts`（输出到临时目录） | 条款排除条件变为新值，摘要改变，`drafts_applied` 记录该草稿 |
| 丢弃草稿后 `--check` | 0 stale，目录回到不可变包状态 |

**仍未做的一步**：把草稿正式提升为**新的包版本**（改 `authoring/` 并编译新 release）。
这一步会改变包摘要与平台当前标准版本，属于显式发布动作，不在编辑器里自动执行。

## 8. 顺带修复的确定性问题

条款目录此前**不可复现**：`clause_retrieval_terms` 迭代 Python 集合，进程间顺序不同，
导致同一份包两次构建得到不同检索词与摘要。已改为排序迭代，连续两次 `--check` 均为 0 stale。
