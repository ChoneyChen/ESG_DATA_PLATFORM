# 提取链路根因审计与工程升级说明（2026-10-14）

本轮的核心判断是：退化发生在执行路线、运行时语义合同、来源身份和资源作用域的连接处。结构化污染物表已经有真实值单元格，却被统一改成多轮导航、阅读、映射；必要量纲在提示编译时丢失；报告层又让不同标准包共用一个模型额度。单独换模型、增加重试或扩大共同额度，都不足以解决这些问题。

本文件以最新紫金矿业 2025 年报告测试为只读审计对象，说明已确认的原因、本轮工作树中的通用修整和仍需真实验收的边界。审计没有重跑报告、修改固定 PDF/IR 或历史成果。工程验收使用匿名合成结构、假模型及临时存储，不使用中国石油失败中间结果，也不把旧紫金成果转为自动测试夹具。

## 2. 按因果关系定位问题

### 2.1 成熟表格路径被报告模式统一绕开

旧 E2-4 路径利用标准字段生成直接填表工作表，模型解释行、列、单位与身份，程序展开真实 IR 值单元格。现有 `DirectFillTemplateCompiler`、表格片段、`GroundingGuard`、Core 物化器和共享来源适配器仍然存在。

本次报告模式曾把所有现代标准包主题交给 `DisclosureSession` 的通用 Agent 路线，包含已经有重复表格合同、真实数字单元格的污染物指标。E2-4 的 19 次调用全部属于理解角色，模板抽取角色为 0。用户选择的抽取模型因此没有真正进入这一类任务。

这是运行策略退化，不是“旧能力的源码已经消失”。修复应在模型调用之前，根据条款含义和当前证据能力选择路线，复用成熟实现。不能按 E2-4 名称写专属分支，也不能失败后偷偷切另一模型。

### 2.2 水污染物已经读到，却在映射阶段被错误排除

固定 PDF 第 174 页含水污染物数据；第 175 页含废气排放数据。水表中的 COD 240.15 吨、氨氮 23.49 吨、总铜 2.47 吨已经被来源阅读处理；总锌 0.81 吨对应行尚未读。水体 Core 为 0 不能解释成“报告未披露”或“OCR 没有识别到数字”。

真实映射输出错误声称水污染物应使用排水体积或浓度，并对铜、氨氮的污染物类别/介质作了错误排除。项目采用的 2023 ESRS E2-4 关注污染物向空气、水体、土壤排放的量；水体是受纳介质，不会把所需污染物质量自动变成排水体积。规范含义应以[2023 ESRS E2 原版本](https://knowledgehub.efrag.org/eng/interactive/esrs-set-1/esrs-e2-pollution/2023-07-31-da/11)及对应数据点合同为准。

标准包 E2-4_02 / E2-4_03 本身保留了 `quantitative_mass`、质量量纲和原编号。断点在 `mapping_cards`：紧凑运行卡片曾删除整个 `measurement_contract`，真实调用输入也确实缺这项。不能把“作者标准包包含质量合同”当成“本次模型已收到质量合同”。

另一方面，COD、氨氮等报告别名或代理量是否满足具体标准污染物分类，还需要明确的语义映射和审核。正确修复是保留量纲、正反定义、受纳介质和不确定状态；不能把所有带“吨”的行都自动批准为标准污染物。

### 2.3 空对象通过协议，未读行被提前放弃

空气来源阅读只处理了硫酸雾、汞、VOC 和颗粒物强度等少量行。氮氧化物 586.30 吨、二氧化硫 1,361.92 吨等真实行仍未读。随后导航返回 `{}`；旧 `AgentPlan.actions` 的默认空列表让这个输出通过了结构校验，任务再以无动作停止。

“可解析 JSON”不是有效工作计划。导航必须给出显式、非空、有限动作，并满足当前真实前沿；未读、待映射、待修复和可以结束的条件分别判断。表头、分区、空行可以作为上下文任务完成，不能要求它们制造事实。

### 2.4 让模型重复抄值引用，增加协议失败和输入规模

实际 9 次来源阅读中有 7 次协议验证问题，包含错误的单元格或跨行引用。这些错误不表示所有兄弟事实都被删除，但会增加无效片段和续读负担。

对结构可靠的表格，后端已有完整真实行与单元格，模型仍重复输出目标值 ID 没有新增语义决策。应该让模型解释行、列与身份，程序展开该真实行的可靠值。正文、视觉修正和结构不可靠来源仍需要自己的引用合同，不能一律取消。

此外，原阅读对象的行顺序受 span 哈希排序影响，首帧没有按物理表格顺序进入重要排放行。本轮将真实页号和结构行号用于行排序，避免 ID 的字典序替代阅读顺序。

### 2.5 真实数值与正确身份没有建立同一条证据链

空气和水表的来源输出缺少完整主体、期间等结构化字段。原始行标签存在，并不意味着已经得到可比较的污染物身份。需要将“值属于这一物理源行”与“这一行已经确认匹配所选条款”连接起来，并保存真实支持片段。

能源表还有更早的结构问题：实际 PDF 的 2025 年覆盖紫金、藏格、合计三个主体列，固定 IR 却把年度 colspan 和企业叶表头对齐错了。22,167.58 GWh 作为 2025 合计，被错误绑定到 2024；21,515.17、652.41 的主体列也受影响。Inventory 已识别表头对齐不确定性，下游自动补年/补主体却未消费这项标记。

本轮修复是不再从矛盾表头自动断言主体和期间，保留原值、原单位、原表头并标为身份待确认。固定 IR 的单元格没有可靠 bbox，不能按猜测挪列并宣称修好了年份。结构问题仍需形成新的明确证据修订。

能源另有“总能源量被假定为可再生能源量”的正匹配。数值准确落在原表里，仍不代表匹配概念正确。本轮将量纲、值族、聚合和易混概念合同传给映射，并要求明确匹配和理由；这能改善合同约束，真实模型是否完全遵守仍须验收。

### 2.6 方法脚注在背景中出现，却没有进入可执行证据范围

PDF 第 175 页脚注说明废气排放量根据检测浓度和尾气流量估算，对应真实 IR `block-p0175-0010`。来源阅读输入已经含这项背景。方法任务却转去读土地管理页面，后来又遇到共享额度停止。

“已在某次背景中出现”与“方法条款可以引用和独立阅读”是两件事。修复通过标准 `explains` 关系连接已选方法条款和已选测量条款，再沿固定 IR 的真实脚注链接，把具体 block 纳入方法证据包。保持同一报告、IR revision、真实 block/span ID；不扩大成整页，也不自动宣布方法披露完整。

### 2.7 不同包独立调用，却共用报告预算账本

用户要求每个标准包是独立任务，这个要求正确。旧实现虽然创建了不同包级 job，实际调用和额度结算却写入同一个报告目录的 `runtime-budget.json`。配置被复制给了每个子任务，资源作用域没有随之独立。

因此，“每次都是单独调用”并不能消除旧实现的共享额度：账本路径决定了累计成本归属。共享证据、缓存和机器执行队列是合理复用；它们不要求共享各包的输入 token、输出 token 或调用次数额度。

本轮规则已经改为：

|层次|资源与职责|
|---|---|
|报告层|编排各包，汇总实际用量；不设隐含的共同模型调用/token 上限|
|包级任务|每个 `job/runtime-budget.json` 保存自己的完整额度、调用和结算|
|包内角色|理解、模板抽取、协议修复共同使用本包账本，避免同一包绕过限额|
|其他包|有自己完整额度，一个包耗尽不会消耗兄弟包的额度|
|报告时间设置|仍保留用户明确设置的整份报告总执行时限，和模型额度分开|

例如配置每包 350,000 输入 token，则 E1-5、E1-6、E2-4 各有 350,000；不是三包均分 350,000。历史实测分别为 102,968、91,663、132,626，虽然总计 327,257，每包均低于这个单包额度。这个重算例子只解释旧停止机制，不证明新运行一定能完成。

旧共同账本保留。只把有真实 `budget_call_id` 调用记录证明归属的历史成本计入其包，原调用 ID 汇总只计算一次。无法归属的历史调用单列；冲突记录报错，不能静默改成零。报告只读接口不会因为查看用量创建或改写模型账本。

### 2.8 输入准入把 UTF-8 字节当作 token

停止前已生成的实测输入为 327,257 token，旧报错显示下一次将到 352,142，大于 350,000。差额 24,885 来自序列化 UTF-8 字节长度，并不是下一调用真实 token 数。不能据此证明下一调用超过剩余的 22,743 token。

字节预留也没有可靠覆盖视觉展开和最终聊天模板。准入和结算使用了不同计量单位，这是资源合同错误。

本轮新增模型输入准入对象：已准备的本地 MLX 运行时使用真实聊天模板和 processor 的 `input_ids`，包括视觉展开；冷启动先保存明确标记的估算，正常加载后在第一次推理前用真实准备结果替换同一调用的预留。计数后的输入张量直接用于生成，避免计数与生成内容不同。没有真正开始生成的失败不冒充已消耗推理 token。

云端或未知适配器的估算仍是估算，单独保留依据；不能为了显示精确数字而假称实测。字符/字节规模用于输入体积管理，不再替代模型 token 结算。

### 2.9 预算错误被显示成超时，恢复建议失真

旧分类器的字符串规则把 `runtime budget` 中的 `time budget` 误当成执行时限；“输入 token”还可能误落到凭据分支。这使输入预算耗尽被显示为超时，用户看不到真实限制。

本轮优先消费生产者类型化错误，包级模型额度用 `model_budget_exceeded`、运行类别和调整任务预算建议表达，保留技术详情。历史错误只用明确异常/已知短语兼容，不再泛化匹配。

普通恢复不会抹掉已发生的包级费用，也不会自动赠送新 token。需要先判断是工作集、片段、协议、来源还是额度问题；已有预算不足时，必须明确调整任务条件或额度，而不是反复点击恢复。

### 2.10 单调用墙钟监督将睡眠/时钟差额计入期限

第一次尝试在北京时间 13:51:21 启动，14:03:03 中断，发生于 embedding 索引。监督记录墙钟约 700.797 秒，其中活跃观察 150.514 秒、未观测 20.072 秒、睡眠或时钟调整 530.170 秒；600 秒外部单调用期限触发。日志不足以单独断言是盖屏、主动睡眠还是其他时钟变化。

第二次在 16:29:36 恢复，17:07:50 失败，活跃观察约 2,292.502 秒；平台报告时间额度 14,400 秒尚余约 12,106.498 秒。这次结束由输入预算准入造成，不能称作报告总超时。两次尝试之间的等待恢复也不属于模型推理时间。

本轮单调用 watchdog 改为跨进程单调活跃期限，另保留独立、较长的墙钟保护。历史监督状态兼容保留。报告总执行时间的整体政策本轮没有重新定义；不能把“单调用时钟修复”写成“所有报告/平台时钟已全面统一”。

## 3. 运行成本应该怎样理解

|生成类型|调用数|实测输入 token|实测输出 token|调用耗时（秒）|
|---|---:|---:|---:|---:|
|规划|16|149,909|1,616|523.403|
|来源阅读|9|124,922|7,772|859.839|
|映射|13|52,426|8,010|636.276|
|合计|38|327,257|17,398|2,019.518|

规划消耗约 45.8% 输入，阅读约 38.2%，映射约 16.0%。逐轮候选菜单、历史、行和引用目录使输入膨胀；E1-5 规划输入由 9,640 增至 18,584。框架调整首先减少结构表格不必要的 Agent 循环，并精简导航中的全表单元格菜单、重复身份细节和不可达 Schema 分支；真实吞吐节省仍需新任务测量。

另有 12 次完成的 embedding 监督调用约 205.845 秒，生成 token 账本不计算 embedding 次数/token，应分开查看。Qwen 7 次加载合计约 17.748 秒，占恢复耗时不到 1%，本次主瓶颈不在模型加载。

本次 38 次生成、17,398 输出 token 都未达到 64 次调用或 65,000 输出上限；格式修复为 0。不能把问题笼统归为“模型总额度全花光”。

## 4. 本轮采用的框架结构

```text
所选原条款 + 标准语义合同 + 固定证据能力
                    ↓
             冻结执行策略描述
              ↙             ↘
      真实重复表格          正文、标量、图像等
      table_series          source_agent
      已选抽取角色           已选理解角色
              ↘             ↙
       来源约束 → Core 合同 → 共享来源/阶段成果
                    ↓
        事实与映射审核 → 规范发布条件 → 正式入库
```

执行策略编译器不改变 ESRS 原编号，不把模型、TopN、prompt 或执行次序塞进作者标准包。核心条款属于标准包；主要条款属于平台阶段选择，仍然保持“主要必须为核心、其他核心不自动扩大输出”。

`table_series` 需要重复定量维度表格合同、必要维度、固定 document/IR/revision，以及当前所选证据中的真实数字表格单元格。缺结构、单值或叙述来源走 `source_agent`。同一主题允许两种路线；直接表格不会被叙述兄弟强制接管。

编译结果冻结原 metric ID、route、role、合同摘要、来源能力摘要、provider 和实际模型身份。checkpoint 没有该描述或描述变化，不能当成当前解释直接复用。路线在推理前确定，不根据某次模型失败偷偷切换。

共享事实是来源层复用，标准映射是语义投影，规范观测是审核/发布层成果。三者分别保存；任何一种执行路线都不能仅凭“程序已有输出”跳过主体、期间、边界、量纲和审核要求。

## 6. 旧路径值得保留什么、不能照搬什么

旧本地与旧云端 E2-4 成果各有 106 个观测，空气 82、水体 24，说明直接表格读取有较高覆盖能力。两份成果同时把 7 个原单位为 `%` 的颗粒物数值绑定为质量指标并标为 `auto_verified`；全部缺完整报告边界和期间起止。

固定 PDF 和 IR 的颗粒物行实际写了百分号。不能为恢复旧数量把 `%` 擅自改成吨。可以保留为报告真实披露来源，是否具备质量指标含义须另行核对；量纲不符时不能进入质量指标规范观测。

应恢复的是成熟表格读取、真实值展开、片段续读和角色执行；不恢复旧乐观可信状态，也不把 106 当作正确答案。

本次没有受控的同提示、同 packet、同合同、同预算模型对照，不能证明“Qwen 本质不如 NuExtract”。模型真实输出确有问题，但路线、合同、可见证据、身份和预算同时发生变化。先固定工程条件，再由用户发起真实对照，才有资格判断各模型的适配效果。

最终故障注入还验证了：大量坏映射的完整诊断留在审计实物中，覆盖状态摘要保持合同长度，因此坏片段不会触发第二次诊断异常或抹掉有效兄弟匹配。匿名正文测试清除了从表格测试对象继承、没有原引用的残留标签，继续保留生产代码对不可引用正文的约束；没有放宽证据条件来让测试通过。污染物身份桥接另明确排除数值目标单元格作为行标签，防止数值被写为污染物名称。

四个本地服务已部署并通过同一版本指纹检查：文档后端、提取后端、工作台前端及数据平台后端。PDF 库、OCR 库、报告库、处理状态、提取会话与模型选项接口均返回正常 JSON。只读核对确认：既有两个队列任务的身份和状态保留；历史 95 条来源事实保留；已发布数据集版本 2/3 的公开观测内容保持一致。历史五包用量可分别归属，全部显示完整的每包 350,000 输入额度；旧终止原因正确显示为模型预算限制。

最终部署版本指纹：`99a8341fd1c75ba48ca961a43dd0c18b8e53eca168270ca03b0ebea27f37225b`。详细上线检查保存在外侧验收目录的 `deployment-status.json`。首次启动核对曾把原始 SQL DTO 与公开 API DTO 直接比较；随后通过既有 ObservationList 响应合同统一两者形状，逐项确认观测内容一致。这项核对方法修正没有修改业务数据。

这些检查验证运行合同和机械边界，不证明真实模型的提取准确率。本轮没有加载模型权重、发起真实模型调用或重跑真实报告，最终验收不使用旧中国石油失败中间结果或旧紫金结果作为测试夹具。真实 tokenizer 吞吐及完整报告质量仍需新任务验收；固定 IR 中已有的错误网格也没有被伪装成已修正。

### 后续真实任务必须逐项核对

1. 由用户发起新任务，保持明确的 PDF 和固定证据版本，不在失败记录上堆重试作为成功证明。
2. 先核对选中的原编号、实际策略和实际模型角色，再检查真实来源覆盖；16 个条款不是 16 个固定数值。
3. 逐行检查空气、水污染物的质量与强度分离、受纳介质、单位、主体、期间、合计/子公司角色和证据。缺字段保持未知或待审，不能补默认值。
4. 方法条款应引用真实脚注；不能只凭其他指标已完成就算它完成。
5. 对能源矛盾网格，先产生明确结构修订或可信视觉证据；下游降为待确认不等于原 IR 已修复。
6. 核对各包自己的用量、错误和未执行项；报告总时间、模型 token、embedding 开销分别衡量。
7. 以“正确来源覆盖、规范身份完整、映射正确、可审核、可发布及单位成本”为结果指标；生成次数、候选数量和进度条不能代替这些指标。

首要目标仍是 PDF → 页面识别 → DocumentIR → 所选主要指标 → 可审核事实 → 规范候选链路可靠运行。后续数据平台比较只能消费满足具体口径的正式观测，不把这次保存的中间数量直接当作平台有效数据。
