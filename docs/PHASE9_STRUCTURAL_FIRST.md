# 阶段 9：结构优先，模型只做语义

日期：2026-10-28  
范围：foundation16 引擎（`kernel.py`、`engine.py`、新增 `structural.py`）。

## 1. 先量后改

计划里写的是“结构优先、模型只在歧义时调用”。实施前先用真实数据回答两个问题：

1. 有多少张候选表的取值列可以由表格结构决定？
2. 如果整张表都交给结构，会不会丢事实？

在 13 份真实 IR 的 95 个候选表任务上实测：

| 方案 | 覆盖率 | 与真实模型答案一致 |
|---|---|---|
| 整表结构决定（选列 + 行映射） | 13/95（14%） | **选列 13/13，行 0/13** |
| 严格版（每个有数值的行都必须被精确命名） | **0/95** | — |

结论：**整表跳过模型会丢召回**。模型在一张表里通常映射 2–5 行，结构只能精确命名其中 1–2 行；
强行跳过会少报事实，这与“以提取准确为第一目标”冲突。因此本阶段不跳过调用。

## 2. 实际落地：结构决定列，模型只做语义

`structural.py` 新增 `structural_column(task, year)`：

- 表内**只有一个**列头含报告年 → 该列；
- 多个同年列时，若某列等于其余同年列的算术和 → 该列（合计）；
- 上述两种情况之外，或存在**没有年份但表头是“合计/总计/合并/total”的兄弟列**（如
  `2025 子公司 | 合计 | 2024 子公司`，合计列的年份由位置表达）→ 交回模型。

决定的列会写进提示词（“The value column is already decided: cN”），模型只负责行映射与注释；
返回后列由结构固定，不再接受模型改判。

## 3. 真实效果（同一批 IR 与历史模型答案对比）

| 指标 | 数值 |
|---|---|
| 候选表任务 | 95 |
| 结构决定取值列 | **83（87%）** |
| 结构决定列 且 模型也给列 | 85 次对比 |
| 与模型一致 | **85/85（100%）** |
| 模型原本没给列、结构补上 | 4 次 |
| 被拒绝（存在模糊合计列） | 12 |

即：不牺牲准确率，把模型每张表都要做的“选列”判断收回到确定性代码；
模型的工作集中在行语义与条款归属——它真正擅长、规则无法穷举的部分。

## 4. 保留的整表结构路径

`structural_decision` 仍然保留，并收紧为：所有带数值的行都必须被精确命名，且至少有一行命中。
在当前真实语料上它决定 0 张表，这是**预期**，不是缺陷：它只在“整张表就是几个条款的直白列表”时生效，
一旦语料出现这种表就会自动少一次模型调用。测试锁定了这条路径的行为。

## 5. 提示词与记录

- 提示词新增一行固定列说明（仅在结构决定时）；
- 记录里 `column_decided_by="structure"`，`conclude()` 新增 `structural_decisions` 计数；
  `model_calls` 只统计真正发生模型调用的表；
- 缓存键（`task_digest`）包含是否固定列，避免新旧答案混用。

## 6. 测试

定向提取 791 通过、6 跳过（新增 11 条结构决定测试：唯一列、同年合计、兄弟合计列拒绝、提示词、精确命名、
名称别名、限定语不被当成单位、子范围标题）。

## 7. 结论与下一步

- **模型调用次数没有下降**，这是实测后的诚实结论：在当前条款与真实表格上，跳过语义映射会直接损失召回。
- 真正减少模型工作量的方向有两个，已排入后续阶段：
  1. **增量映射**（阶段 3 已做缓存版）——新条款复用已理解的对象，不重复读表；
  2. **条款侧的结构算子**——把“行名等于条款别名”“行名在条款别名集合内”这类可判定情形登记为算子，
     由条款 profile 声明，而不是全局猜测。
- 下一步（阶段 10）转向数据库科学模型：把已经确认的口径、证据和观测做成稳定的一等结构。
