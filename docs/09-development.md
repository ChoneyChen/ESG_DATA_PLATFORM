# 开发与维护流程

目标是让需求、责任、合同、实现、真实结果处于同一次变更里；不是增加审批、无用校验或文档数量。

## 每轮工作顺序

1. 读docs入口→需求→架构→所属模块→合同→对应专题。先确认用户要求和当前代码，不以旧审计结论直接决定修复。
2. 写清最短问题定义：真实触发、首个偏离点、期望行为、涉及RQ、所属模块。小修可放任务说明/提交描述；不必新增计划文件。
3. 决定修改哪份权威：条款语义/词典归单条；通用数据类型归contracts；物理结构归document；阅读额度归extraction策略；调度归pipeline；比较/发布归database；表现归前端。
4. 先对照合同和上下游消费范围，再修改责任实现与相应规范；删除替代的分支/说明，避免第二套定义。
5. 按变更风险直接跑相关真实任务，观察它自己执行并检查输出。不得手填量值、替链路写事实或干预生产批次来制造通过。
6. 如涉及文件/HTTP，重建参考索引；如涉及DTO，生成客户端类型/Schema。对文档修改，只需生成和链接/内容核对，不启动模型或生产任务。
7. 在质量清单更新结论和未完成项，在CHANGELOG写简短结果；提交清楚的问题、行为、证据和边界，按授权推送。

## 生成命令

```sh
ExtractESG/.local/python/bin/python tools/build_documentation.py
ExtractESG/.local/python/bin/python tools/check_contracts.py --write
```

check_contracts --write统一生成Schema、Console类型和数据库类型，并重建条款索引，不要接着重复运行分项生成器。仅改客户端类型出口时可单独用tools/export_console_types.py或database/scripts/export_contracts.py。合同/类型命令仅在相关合同变化时执行；生成器CLI如后续改变，同轮更新本节。JSON Schema、数据库类型SDK、前端contracts.ts是代码合同的投影，不是独立手写语义。build_documentation只解析第一方源码，不导入服务、不连接数据库、不读取生产运行数据。

## 真实验证及成本

业务变更以真实PDF任务为主要验证，选择能复现该故障的报告和条款，并观察同一任务的准备、候选、调用、结果和必要下游行为。只扩大到受影响范围，不因文档/小修重跑全部模型任务。现有必要合同/事务测试按实际风险使用，不为每次修复新增镜像实现的测试套件。

记录：代码/引擎与条款版本、输入资源和选择、预算、会话/运行ID、实际状态、值/期间/单位/关系、调用/tokens/耗时和剩余问题。模型耗时、worker活动、排队和OCR准备分开，原值数/目标数不是准确率。开发产物存`.local/development/`或隔离数据根，当前规范只保留有用结论。

## 兼容与变更控制

接口或字段含义改变，先明确新旧消费者及旧冻结数据读取策略；破坏性改动提升合同版本。单条编辑使用expected_digest；发布预览/资源修订沿用各自并发语义。不要为“向后兼容”恢复已退役体系，也不能静默重解释旧事实。

数据库迁移只追加、不改已应用文件；启动不代做迁移。服务代码变更后部署指纹要反映实际运行包，不能仅修改源码而宣称模型worker已更新。恢复旧任务若需新执行代码，明确交接，保持冻结输入和已存事实身份。

## 提交与协作

任何工作区、终端、IDE或AI代理都从根AGENTS进入同一docs。模块README只链接规范，不复制参数/流程。没有新的“某轮总架构”“当前状态2”“临时标准手册”。架构决定在02原表更新，实际问题在10原表更新。

提交只含本轮相关文件；不夹生产数据、凭据、依赖或CrawlESG。说明采用“问题→最终行为→真实证据→剩余边界”，不把尝试过程堆成文档。完成轮次按已授权身份提交/推送，生产发布仍是业务显式操作。

## 一轮完成的定义

对应需求与责任明确；实现和上下游合同一致；被替代内容已退出当前路径；实际受影响任务/页面或纯文档生成已经证明目标；已知剩余问题诚实保留；文档、索引和提交一致。仅写了规划、编译通过或服务注册了接口，都不能替代真实业务效果。
