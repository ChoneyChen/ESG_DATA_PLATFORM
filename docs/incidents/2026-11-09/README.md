# 50份报告任务停滞修复

2026-11-09，Asia/Shanghai。提交的是50个不同PDF，每份选择基础32个独立条款。本次保留原任务ID、PDF、冻结条款、预算及已保存原值，修复后继续运行。

## 实际卡点

1. **错误记录使执行接口返回500。** 第一份First Solar运行在E1-5_01读取中遇到输出截断，错误记录携带`frame_key`；`RunError`未声明它，NativeRun响应验证失败。该任务已有7条原值，随后需要补页，但编排无法读到状态；整个列表也被同一条记录拖成500。补齐错误合同，让错误能被显示和恢复。
2. **50份状态轮询形成重复跨服务读取。** Console列表、浮窗和编排各自逐任务读取，且反复解析冻结合同正文。文档API健康检查失败、列表超过12秒。本轮增加批量状态端口，在SQL投影时排除合同正文，列表和编排共同消费该端口；冻结合同仍由执行端独立读取。
3. **控制日志写入量过大。** 控制库约4.89GB，准备事件77059条；事件JSON约3.78GB。协调器每轮解析包括已结束任务的全部状态，心跳/耗时变化又写整份配置和结果。改为只扫描活动准备任务，忽略纯时钟变化，事件只记录步骤、状态与错误等变化，增加按处理任务读取事件的索引。历史记录保留，没有重置数据库。
4. **数值文本重试没有拆掉数值行。** 旧split_frame对text切文本，但数字rows仍是原集合，导致再次输出同一大批选择和属性，重复触及4096输出预算。定量按实际行/列拆分，并在调用前按输出预算分段；定性继续按文本拆分。所有数值仍有原位置和绑定，不缩小条款选择或删原值。实际部署暴露output_budget枚举遗漏，已补齐，相关两份任务已恢复。
5. **运行与排队不易辨别。** 本机模型使用共享执行锁逐项运行。50份已完成初始准备后，单个阅读worker占槽，其余正常等待；“0/32”只表示还没有结束第一条，不能表达正在生成。浮窗现分别显示运行/排队数量、当前条款、调用数与生成token；停止服务时先等待编排退出，再停止其依赖的提取API，已退出的僵尸进程不再被当成活跃服务。

## 恢复与实际观察

原50份尚未封存任务显式切换到修复后的执行代码，各自记录engine_upgrades的前后指纹与原因；冻结目标摘要、原任务ID和原值不改写。队列中未执行的任务继续使用原身份；停机时中断或本轮修补时失败的任务按原检查点重新入队。未变更报告和条款内容，未切换云模型，自动发布关闭。

原来两份启动失败的真实物理帧也使用当前分段协议读取，保留全部原单元位置。新准备事件体积119/443字节；观察期间没有继续写入数十到数百KB的整包快照。
