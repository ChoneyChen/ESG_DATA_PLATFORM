# 批量任务调度饥饿与续跑优化

2026-11-09，Asia/Shanghai。本轮只修复批量任务内部执行与调度；监督使用只读状态和实际产物，不代替报告阅读，不补值，不改变PDF、32条选择、报告总预算或冻结条款。

## 重新定位的根因

上一轮修好了接口500与状态轮询，但新增31条原值只证明单次阅读能执行，没有证明50份任务的后续依赖能持续推进。此次发现：50份中37份等待补页，11份排队，1份实际阅读，1份已部分结束。最早的补页续跑链路已滞留约12小时；其中一个OCR子任务直到排队9小时26分钟后才获执行。控制台将等待补页也计入运行，形成“38份正在运行”的假象。

主因是执行粒度与队列顺序不匹配：整份报告最多32条、128次模型调用占一个阅读worker；补页OCR及IR排在同一FIFO队列后端。补页完成后的阅读和OCR后的IR又重新入队，准备与阅读相互挤压。模型进程仍生成，不属于无进程的锁死；问题在于批量依赖长时间得不到执行机会。

## 模块化修复

| 模块 | 更新与文件 |
|---|---|
| 统一队列 | `ExtractESG/pipeline/src/esg_pipeline/store.py`：准备与阅读交替取任务；准备侧先完成已具备识别结果的IR。保留原队列任务和业务输入，不手工移动某份报告。 |
| 提取主干 | `ExtractESG/extraction/src/esg_extraction/pipeline/engine.py`：在模型调用的保存边界短暂让出执行；正常每轮两次调用。每次调用保存未读分段、父调用及尝试次数，补读位置继续保存；续读保留同一物理帧已有的失败状态。让出不计入失败或完成。 |
| 执行适配 | `pipeline/runtime.py`、`worker.py`、`state.py`：让出时退出worker并释放模型锁，原生任务保持queued，既有事实、累计调用和总预算保留；轮次完成与整份报告完成分别表达。 |
| 编排续跑 | `ExtractESG/pipeline/src/esg_pipeline/extraction.py`：已完成的轮次使用新的调度键续跑同一个run，避免幂等键返回旧轮次造成无法再次启动。 |
| 补页恢复 | `ExtractESG/extraction/src/esg_extraction/pipeline/api.py`：从原检查点恢复已完成条款数，不再将条款进度暂时归零；调用、原值与总预算保持累计。 |
| 状态窗口 | `ExtractESG/contracts/src/esg_contracts/sessions.py`、`ConsoleESG/backend/src/esg_console/monitor.py`及前端运行窗：区分实际执行、等待补页、排队；有补页请求时不沿用旧阅读阶段。 |
| 部署交接 | `ConsoleESG/scripts/upgrade_pending_execution.py`：显式、仅针对维护前的待执行快照交接代码版本，保留合同摘要、请求、事实与检查点，记录前后代码指纹；已封存的部分结果和用户主动取消的任务保持原状。 |

当前部署为clause-backbone-1.9。49个尚未结束的原任务完成代码交接，另1份既有部分结果保留。观察记录见[runtime.json](runtime.json)。

同一个run已观察到累计14→16→18次调用；另一任务累计8→9→10次，读取剩余大表分段后事实由10条增至12条，再正常让出执行槽。旧的输出截断任务也自行拆分证据并保存未读部分，没有人工代读。
